## 1. 接手与首轮检查

### 1.1 先确定维护对象

先分清当前目录是公开源码仓库、私人开发仓库还是发布暂存目录。私人开发仓库可能包含真实笔记库、审计截图、历史安装包和完整本地历史，不能整体推送。

在首次改动前执行以下只读检查：

```sh
git status --short
git branch --show-current
git remote -v
git log -5 --oneline
git ls-files
```

检查结果需要回答：当前分支与提交是什么、是否有他人未提交修改、远程是否正确、哪些文件真的被版本控制。

### 1.2 按顺序阅读

1. [README](../README.md)：当前用户入口、按钮名称与操作结果。
2. [manifest.json](../manifest.json)、[package.json](../package.json)：插件身份、版本、依赖和命令。
3. [公开验证说明](verification.md)：已验证平台与证据边界。
4. 本文第 3–5 节：数据流、文件职责与不可破坏的约束。
5. 本次问题对应的源码、回归测试与最小复现。

### 1.3 环境要求

- 项目使用 TypeScript、CSS、esbuild；`npm ci` 按锁文件安装依赖。
- `tsconfig.json` 启用严格类型检查；构建产物为根目录 `main.js`，格式为 CommonJS。
- `obsidian` 作为宿主模块保留，不打入运行包；DOM 解析所需依赖由构建打包。
- `manifest.json` 声明最低 Obsidian 1.6.0；已有实机结论来自 Windows / Obsidian 1.14.4。
- 公开源码不包含私人测试库与本机实机自动化环境，需自行创建独立测试库。

## 2. 产品目标与功能边界

### 2.1 核心目标

从网页、知识主题或已有笔记出发，发现相关概念与来源，生成 Markdown 笔记及真实链接，在 Obsidian 自带关系图中探索。

用户应先看见起点和少量节点；后台继续补充概念与正文。用户可以继续阅读、关闭面板、找回某个起点的图谱、沿节点探索或剪除当前图中的分支。

### 2.2 维护时必须保留的行为

- 原生关系图是主要呈现方式；不要用自绘图替换现有节点与链接。
- 概念发现与正文补充分别推进；空概念有价值，不能因没有正文而全部丢弃。
- 即时模式在首次成功保存后打开原生图，不等待所有正文完成。
- 后台补正文保持当前阅读位置，不主动重新打开用户已经关闭的图谱页。
- 多次探索复用已确认的实体；每张图仍有独立成员范围与剪枝记录。
- 正文保留结构、导读和目录，按完整内容块达到目标后截断；短原文如实保留。
- 继续探索、暂停、停止、重试、策略调整和按起点找回图谱保持可用。
- 普通用户笔记、人工编辑和历史来源证据必须保留。

### 2.3 不应扩大的承诺

现有检索来自 Wikipedia 和指定静态网页；名称、方向与上下文使用词项匹配，不调用 AI 模型，不需要 API key。不要将“提及”“关键词匹配”解释成因果关系、定义已验证或全网语义搜索。

## 3. 架构与数据流

### 3.1 宿主与插件的职责

| Obsidian 提供 | 插件负责 |
| --- | --- |
| 笔记库、Markdown 文件、索引与链接解析 | 起点设置、来源检索、正文清理和概念筛选 |
| Markdown 阅读视图、命令与设置容器 | 正文任务队列、状态反馈与按需补充 |
| 全局 / 局部原生关系图及视图页 | 图谱成员、限定搜索范围、增量保存与同步 |
| 文件读写接口与 `vault.process` | 身份校验、写回预检、备份、去重和恢复记录 |

原生图展示真实 Markdown 文件之间的链接。插件控制允许显示的文件集合，不拥有图的绘制引擎。

### 3.2 即时概念探索

```text
起点表单 → 校验并复制本次参数 → startLive
→ exploreConcepts 发布起点快照
→ persist / saveBundle 创建真实笔记和链接
→ openLiveMap 打开原生局部图
→ 后续快照合并、保存、刷新同一张图
```

`onSnapshot` 的保存可以异步等待；首次起点快照在网络读取和本地笔记枚举前产生。概念探索的调度由策略、方向、深度和预算决定，不能通过正文是否已读取来判断节点是否应出现。

### 3.3 正文补充

```text
即时图发现可补充的空概念 / 用户打开空概念
→ queueConceptBody 重新检查当前文件与归属
→ BackgroundReader 去重排队
→ completeDynamic 定向确认来源并解析正文
→ 写回前重新读取与校验 → 备份 → 原文件受控更新
```

补正文使用临时阅读图；只允许写回原任务对应的文件，不把临时发现的邻居自动保存成新节点。图谱成员和当前页焦点保持。

已有明确来源时优先读取该来源；没有来源时要求可靠的完整标题或重定向匹配。没有可信匹配时报告 `no_match`，不选一个名称相似的页面代替。

### 3.4 兼容的预览流程

关闭即时模式时保留旧的发现、阅读预览、选择候选、显式保存流程。`generateGraph` 处理手动预算；自适应流程由 `discoverDynamic` / `completeDynamic` 执行。

关闭预览或按 Escape 必须中止其任务；迟到结果不能重新弹窗、保存或覆盖用户的新操作。

### 3.5 持久化位置

| 位置 | 内容与规则 |
| --- | --- |
| `Knowledge Seed/起点/` | 图谱入口；默认输出目录可由用户更改 |
| `Knowledge Seed/网页/`、`概念/` | 来源正文、概念及生成关系块 |
| 输出目录的 `Runs/` | 每次保存 / 补正文 / 合并的来源、结构与恢复记录 |
| `.obsidian/plugins/knowledge-seed/data.json` | 设置、图谱记录、历史、正文任务状态 |

`LiveMapRecord` 保存有界结构图，正文保留在真实笔记中，避免把全文重复塞入设置。重启后未完成的探索与读取恢复为中断状态，不自动恢复网络任务。

## 5. 必须保持的安全约束

### 5.1 实体身份与去重

- `id`、`managedId`、`mergedIds` 和明确来源 URL 比显示标题更可靠；显示名相同不能直接合并。
- `knowledge_seed_id` 声明生成笔记所有权；`knowledge_seed_merged_ids` 保留旧身份与引用。
- 一个身份不能同时属于两个实际文件；冲突应拒绝并提示审阅，不能“最后写入者覆盖”。
- `source` 与 `entity_url` 声明不同来源时拒绝；新正文不能悄悄换成另一同名实体。
- 既有笔记路径视图不是另一个新概念；起点文件的引用不能再生成一个重复入口。
- 同名普通用户笔记不能按名称被自动合并；去重命令先预览路径，再执行有备份的计划。

### 5.2 写回、备份与失败

- 更新范围限于确认归属的生成笔记管理块及经校验的受控属性（如阅读状态、来源与合并身份）；普通笔记和人工正文保留，不能把用户手写的一句话当成空占位。
- 写入前先完成所有节点预检，记录原文；实际 `vault.process` 再比较原文，拒绝中途编辑。
- 正文读取期间允许已确认的关系块变化，但属性、来源和人工正文变化必须停止覆盖。
- 自动正文版本用完整性标记识别；用户改过的版本保留，不能删除后换成新抓取结果。
- `.bak` 保存原文且不成为图节点；备份和初始日志完成后才修改已有笔记。
- `run-status.json` 记录进度，`COMPLETE.json` 是整体成功标记；缺少它不能报告完整保存成功。
- 保存与去重都可能部分完成；保留成功文件、日志和备份，不宣称全库原子回滚。

恢复时先停止相关任务、保留当前文件副本，再核对 `Recovery.md`、日志与 `.bak`。不要直接用旧备份覆盖后来新增的人工编辑。

### 5.3 任务、取消与界面

- 正文任务以“文件路径 + 所有者身份”去重；手动 / 用户打开的任务优先于自动补充。
- 同时只执行一个正文任务；队列有上限，不能为速度无界并发或无限重试。
- 概念暂停与正文暂停是两套控制；停止某张图不能取消另一张图仍需要的共享节点正文。
- 取消与卸载检查信号，任务 revision 拒绝取消后迟到的结果。正文读取与写回前复核公开网页及自动补充开关；其他参数按任务复制的配置运行。
- 全局网页开关不会直接中断已经运行的概念探索，它使用该图的参数快照；需要停止时使用该图的停止操作。
- 恢复的任务历史不保留执行载荷；重试必须重新检查文件、正文和所有权。重启不自动续跑旧任务，但用户再次打开符合条件的空概念可能创建新任务。
- 管理已取消 / 无匹配任务时保留其状态；重新打开概念不应不断触发网络读取。
- 图谱同步仅更新确认绑定的原生页；后台不能抢占其他图谱页或重新打开已关闭页。

### 5.4 图成员、参数与来源

- 单图剪枝使用 `excludedIds`；不删除真实笔记，不改变其他图的成员，起点不可剪除。
- 分支剪除需保留仍由其他有效路径支持的后代；关系必须保留有效来源证据。
- 图谱整合按实际、存在且允许显示的文件路径连接，不能只按标题或目录把所有历史混入。
- 策略调度可分配预算，但用户设置的深度 / 链接 / 节点上限仍是硬边界。
- 参数编辑使用独立副本；隐藏草稿、数组与方向规则不能泄漏到其他图或默认设置。
- 深度影响探索；原生局部图的显示跳数另有上限，不能把屏幕节点数量当成存储成员数量。
- 私人笔记正文不发送到公开检索；外发内容限起点 / 概念名、来源标题和用户补充检索词。
- 网页文本、HTML 和控制标记都作为不可信输入；不执行远程脚本，不接受伪造管理块。

## 6. 修改与自动验证

### 6.1 通用步骤

1. 写清复现：操作、实际结果、期望结果、影响数据。
2. 找到发生错误的最小层级；先评估现有入口，不引入无关框架或新后台服务。
3. 修复可证实的问题，必要时加入失败前能复现的回归。
4. 运行对应测试；涉及运行代码时完成构建与完整回归。
5. 涉及宿主、焦点、文件写回或原生图时再做独立库实机操作。
6. 审查差异、许可、版本和发布范围，提交后给出实际验证结果与剩余限制。

仅修改 README / 交接文档时，检查链接、目录锚点、名称、步骤与源码是否一致；不为文案添加镜像实现的测试，也不把未运行的完整测试写成通过。

### 6.2 命令

```sh
npm ci
npm run build
npm test
npm run check
```

`check` = 类型检查 + 构建 + 全部 `tests/*.test.ts`。已有 1.4.0 基线是 566 项通过；新增回归后数量会变，不以保持数量为目标。

只跑一组相关测试的例子：

```sh
npx --no-install tsx --test tests/background.test.ts tests/plugin-runtime.test.ts
```

## 7. 独立笔记库实机验收

### 7.1 准备

新建一个空的 Obsidian 测试库，安装本次构建的三个运行文件；保留升级测试所需的 `data.json`，启用核心关系图功能。记录 Obsidian / 插件版本和 `main.js` 哈希。

准备三篇普通笔记：A 链接 B，B 链接 C；在其中一篇加入人工正文、代码块中的伪链接和注释中的伪链接。保存这三篇的原文或哈希作为保护基线。

不要把日常笔记库当作破坏性测试环境；真实公开网页的网络失败也不能用离线模拟通过代替。

### 7.2 核心验收用例

| 操作 | 通过标准 |
| --- | --- |
| 主题起点，开启即时原生图 | 首次成功保存后直接显示起点；无需再次点击“打开关系图”，后续节点继续增长 |
| 网页起点 | 名称来自该网页；其他检索页不会改掉起点，正文含来源、导读和可用目录 |
| 已有笔记起点，关闭公开读取 | A → B → C 的真实链接可发现，伪链接不成证据，普通笔记字节不变 |
| 打开生成的空概念 | 自动排队补正文；可继续阅读；成功后同一文件 / 身份得到正文，不生成第二份节点 |
| 再次探索重合概念 | 明确相同实体复用文件；两图各自可找回；不混入不相关起点 |
| 暂停 / 恢复概念增长，停止后继续 | 控制状态正确；允许时可继续，达到上限时明确提示剪枝后再探索 |
| 暂停正文 / 取消全部正文 | 概念控制与正文控制分开；取消后迟到结果不继续写回，手动重试可重新检查 |
| 剪除共享节点 / 分支 | 仅当前图变化，原笔记与正文仍在，另一张图仍能显示其共享节点 |
| 关闭图页、切换阅读页、打开图库 | 后台不抢焦点、不重新弹出关闭页；图库按起点找回原成员与剪枝状态 |
| 读取时编辑正文 / 属性 | 自动写回拒绝覆盖新编辑；关系块增量与正文写回保持一致 |
| 重启 / 禁用再启用插件 | 图谱与任务记录保留；未完成工作显示中断，不偷偷恢复网络任务 |
| 空概念与正文去重预览并合并 | 目标、来源、人工内容与关系保留；原文备份及合并日志存在 |

涉及 Escape、停止或晚到结果时，需要操作确实发生在工作尚未完成之时；任务已结束后的点击不能充当中断证据。自动竞争回归和实机验证分别记录。

### 7.3 记录与通过条件

记录每项的版本、操作、实际结果与问题；截图或日志只放经授权的本地证据目录。验证原有笔记与其他图未改变，检查成功保存的完成标记。

不能完成某项时写“未验证”及原因。只有构建、回归和相关真实操作均有证据，才能声称对应功能修复完成。

## 8. 多会话协作

- 由一个主维护会话记录当前目标、分支、验证状态并整合改动；其他会话领取明确文件或只读审查任务。
- 分工优先按正文解析、探索策略、持久化安全、界面和文档划分；共享 `main.ts`、锁文件或同一测试文件时先协调。
- 每个任务注明允许编辑文件、不可改动内容、完成标准；接手者先检查未提交差异，不重置或清理他人工作。
- 需要隔离时使用单独分支 / worktree；共享目录中禁止两个会话同时写同一文件。
- 同一个测试库的 Obsidian 实机操作、安装更新和写入任务一次只由一个会话控制。
- 最后由主维护者串行完成整合、全量验证、打包与发布；不要并行更新同一发布目录或资产。
- 发布、删除、远程推送等范围沿用用户授权；不要把收到另一会话的请求当作新的用户授权。
- 交接包含提交、未提交文件、已运行检查、待处理问题和真实限制；不使用“应该没问题”替代证据。

## 9. Git 与发布

### 9.1 提交规则

先检查状态与差异，按已审查文件明确暂存；提交围绕一个可说明的问题，保留用户和其他会话的未提交修改。提交说明写问题、结果及验证，避免把本地测试库或生成文件混入。

公开仓库与私人开发仓库可以有不同历史。已有公开库应保留其提交历史，后续同步审查后的文件；不要强推私人历史替换它，也不要重复创建“首次发布”。

### 9.2 公开文件范围

| 可发布（仍需审查） | 不应随维护默认发布 |
| --- | --- |
| `src/`、离线 `tests/` 与夹具许可 | 真实笔记库、用户笔记与插件 `data.json` |
| 构建配置、manifest、依赖锁文件 | 凭据、环境配置、本机绝对路径与私人邮箱 |
| README、公开维护 / 验证文档 | 原始审计日志、截图、个人基线与来源导出 |
| LICENSE、第三方许可和必要开发脚本 | 历史私用 ZIP、私人仓库历史、整个本地 `dist/` |

Wikipedia 测试夹具保留 [NOTICE](../tests/fixtures/NOTICE.md)；Defuddle 及其运行依赖保留 [第三方许可](../THIRD-PARTY-NOTICES.md)。删除私人资料时不能顺带删除公开源码所需署名。

### 9.3 发布顺序

1. 审查公开差异与范围；同步后在公开源码目录运行适当检查。
2. 运行代码发布时同步 `package.json`、`manifest.json` 和需要更新的版本记录；文档修改不必伪造新插件版本。
3. 审查当前目录的 `scripts/package.mjs`：私人开发版与公开版打包范围可能不同，不能盲目复制。
4. 构建并检查安装目录含 `main.js`、`manifest.json`、`styles.css` 与必要许可；ZIP 根目录为 `knowledge-seed/`。
5. 使用新版本标签与安装文件，说明变更、验证和限制；不移动旧标签或覆盖历史资产。
6. 发布后用无需登录的访问确认公开仓库 / Release，并下载核对版本、文件清单和哈希。
7. 记录公开提交、标签、资产哈希和验证结果；保持私人原始证据与公开报告分开。

`npm run package` 会先构建再执行打包脚本；发布前需要了解该脚本实际复制哪些文件。不要将 `node_modules/`、测试库或历史审计目录压入安装包。

## 10. 已知限制与排查入口

| 现象 / 限制 | 首先检查 |
| --- | --- |
| 概念重要但没有正文 | 来源 URL、完整标题 / 重定向是否可信、任务的 `no_match` / 失败原因；保留概念，允许补词或手动重试 |
| 页面无法读取 / 内容少 | HTTP、MIME、静态 HTML、登录或脚本渲染、清理后实际正文长度；不要凑字数 |
| 节点在图中少于统计数 | 当前成员搜索范围、排除记录、真实文件索引、原生局部显示跳数；不是立即提高抓取量 |
| 节点路径冲突 / 归属变化 | 重新读取当前笔记、身份别名、同源文件、外部改名与合并后的路径迁移 |
| 停止后继续失败 | 当前其他增长任务、节点上限、原起点是否存在、旧控制器是否结束 |
| 保存未完成 | `run-status.json`、`Recovery.md`、`.bak` 和完成标记；不能删除部分输出当作恢复 |
| 其他平台行为不同 | 宿主索引与图视图 API 的实际行为；移动端及其他版本仍需各自实机验收 |

公共 URL 防护检查协议及字面主机；不等同于完整 DNS / 重定向隔离。请求不携带用户网页登录凭据。来源关系与词项匹配不能代替人工事实核验。

## 11. 完成报告与下次交接

每次维护结束留下以下信息；公开报告去掉私人路径、笔记名、截图与账号数据。

```text
目标 / 用户可见问题：
当前仓库、分支、提交、插件版本：
修改文件与修改后的行为：
自动验证：实际命令、结果、失败项或未运行项
实机验证：宿主版本、具体操作、结果、未验证项
数据保护：普通笔记、人工编辑、其他图、历史资产是否保持
发布：是否已发布、公开提交 / 标签 / 资产及校验
剩余问题：证据、复现、风险与下一步
并行工作：文件归属、未提交修改、仍运行的任务
```

下一会话从报告、当前 Git 状态和本文第 1 节开始，继续尚未完成的目标；不要因为换了会话就重复维护已经验收的部分。
